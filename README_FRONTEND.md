# Frontend Documentation

## 1. Frontend Overview

### Purpose
The frontend is the client-side React application for the AI Financial Analyst platform. It provides a browser-based interface for users to register, log in, manage companies, upload financial reports, and view AI-generated analysis.

### Responsibilities
The frontend is responsible for:
- Showing pages for authentication, dashboards, company management, reports, and report details
- Collecting user input from forms and uploads
- Calling the backend API through a centralized Axios client
- Managing authentication state and protected routes
- Rendering analytics content and loading states clearly

### Why the frontend exists
The backend can expose data and services, but users need an interface to interact with them. The frontend turns the API into a usable product for end users.

### Problems it solves
The frontend solves the following problems:
- It provides an interactive experience instead of raw API calls
- It keeps users informed with loading, error, and success states
- It protects routes that require authentication
- It turns backend responses into readable dashboards and tables

---

## 2. Frontend Architecture

The frontend uses a simple React application structure built with Vite.

```text
Browser
↓
React App
↓
Pages
↓
Components
↓
API Layer
↓
Backend
```

### App Layer
The main application entrypoint renders the app and wires up global providers such as authentication context.

### Pages
Pages represent the main screens in the UI, such as login, registration, dashboard, companies, reports, and report detail.

### Components
Components are reusable UI elements such as the navbar, sidebar, modal, loading spinner, and error message display.

### API Layer
The API layer provides a collection of modules for authentication, companies, reports, and analysis. These modules are responsible for making HTTP requests to the backend.

### Why this architecture is simple and maintainable
It keeps the codebase modular. Pages define the user experience, components provide reusable UI pieces, and the API layer keeps network communication isolated from the UI.

## 5. Request Lifecycle

The request lifecycle describes how the frontend requests data from the backend.

```text
User action
↓
Page component
↓
API helper
↓
Axios instance
↓
Backend API
↓
Response handling
↓
UI update
```

### User action
The user clicks a button, submits a form, or uploads a file.

### Page component
The page component receives the event and gathers any necessary data.

### API helper
The page calls a helper in the API layer such as `authApi.login()` or `reportApi.uploadReport()`.

### Axios instance
The helper uses the shared Axios instance to create a consistent HTTP request.

### Backend API
The request goes to the backend, which validates and processes it.

### Response handling
The frontend receives the response and updates local state or navigates to a new page.

### UI update
The UI shows the result, such as a successful login, a list of reports, or an error message.

## 6. Core User Flows

### Registration flow
1. The user visits the registration page.
2. The page collects email, password, and name.
3. The auth API calls the backend registration endpoint.
4. The user is redirected to the login experience or dashboard.

### Login flow
1. The user enters credentials.
2. The frontend calls the backend login endpoint.
3. The JWT is stored in the application context.
4. Protected routes become available.

### Company management flow
1. The user navigates to the companies page.
2. The app requests the company list from the backend.
3. The user can create, edit, or delete records.
4. The UI refreshes the list after each action.

### Report upload flow
1. The user navigates to the upload page.
2. The user selects a company and uploads a PDF file.
3. The frontend sends the file to the backend.
4. The backend returns a report object.
5. The app displays a success state and can navigate to the report detail page.

### Report analysis flow
1. The user opens a report detail page.
2. The app requests the report and its analysis from the backend.
3. If no analysis exists, it triggers the analysis endpoint.
4. The result is displayed to the user.

## 7. State Management

### Authentication context
The app uses `AuthContext` to manage:
- whether the user is authenticated
- the current authenticated user object
- the access token
- login/logout actions

### Local component state
Pages and forms use React state to manage:
- form inputs
- loading states
- validation errors
- modal visibility
- selected company/report data

### Why this approach works
The app is not large enough to require a heavy global state management library. React context and local state are sufficient and easier to maintain.

---

## 8. API Integration

### Base URL
The API layer uses a base URL configured in Axios to target the backend.

### Authentication headers
When the user is logged in, the Axios instance automatically attaches a bearer token to requests.

### Error handling
Errors from the backend are commonly handled by:
- showing an error message component
- stopping loading states
- returning to the previous page if needed

### File uploads
The report upload flow uses multipart form data so the PDF file can be sent to the backend.

## 9. Styling Approach

The frontend uses CSS files that are organized per page or component.

### Why this approach is used
- It keeps styling close to the UI files
- It allows page-specific customization
- It avoids the need for a large shared design system in the current MVP

### Notes
The styling is functional rather than highly design-system-driven. The app currently focuses on clarity and usability over polished visual design.

---

## 10. Security Considerations

### Authentication protection
Protected routes ensure that only authenticated users can access certain pages.

### Token storage
The app stores the access token in frontend context and uses it for API requests. In a production app, token storage should be handled carefully and possibly moved to a more secure mechanism.

### Route protection
The private route component prevents access to protected pages if the user is not logged in.

### Input validation
The frontend uses forms and state handling to reduce invalid input, but backend validation remains the source of truth.

## 11. Scalability and Maintainability

### Current scale
The current frontend structure is appropriate for a small to medium-sized application with a few core workflows.

### Where it may need improvements
As the app grows, the following improvements would help:
- Split pages into more focused components
- Introduce a reusable form system
- Replace repeated API request logic with a more advanced service abstraction
- Add better state management if the app becomes more complex
- Improve test coverage around route protection and API integration

### Maintainability strengths
The app already benefits from:
- clear separation between pages and components
- dedicated API modules
- context-based authentication management

---

## 12. Frontend Summary

The frontend is a React + Vite client that provides a simple but effective user experience for the financial analysis platform. It offers authentication, company management, report uploads, and report-detail views while keeping the UI organized into pages, components, and API modules.

### Why this architecture was chosen
It is straightforward and accessible for a product MVP:
- React enables a component-oriented interface
- Vite provides a fast development experience
- Axios centralizes network code
- Context keeps authentication state simple

### Possible future improvements
The frontend could be improved by:
- adding stronger form validation
- introducing a design system or component library
- adding end-to-end tests
- improving error handling and loading states
- improving route-based loading and performance optimizations
